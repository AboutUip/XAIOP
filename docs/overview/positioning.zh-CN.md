## 1. XAIOP 解决的问题

传统方案（JSON / XML）是为**确定性程序**设计的格式，要求生成者一次性、无差错地吐出最终的完整结构——括号必须配对、层级必须精确计数、任何一处偏差都会让后面全部作废。

这个要求本质上是在考验**记忆**：模型要在生成过程中持续追踪自己写到第几层、括号还差几个没闭合。

XAIOP 把这个要求换掉了。它不要求模型描述「最终结果长什么样」，而是让模型编写一串**构造指令**（进入 / 回退 / 匹配 / 重置）——用一个游标在数据树上走一遍，SDK 负责把这串指令确定性地解释成 JSON。

模型要维护的不再是「全局结构的正确性」，而是「下一步该往哪走」这个**局部判断**。

**用一句话概括：** 把「记忆问题」转移成了「逻辑问题」。直接输出最终 JSON，某种意义上是在生成「结果的汇编代码」；XAIOP 让模型写的是更接近它天然擅长的、可以逐步推理生成的操作序列。

---

## 2. 已经验证的部分

七场真实基准测试（GPT-5.6-terra / Gemini-3.6-flash / DeepSeek-v4，各含原生 + 兼容模式）显示出一条清晰的规律：

**XAIOP 的收益和模型自身 JSON 能力成反比。**

| 模型画像 | 观察到的规律 |
| --- | --- |
| JSON 基线较弱（如 GPT） | XAIOP 带来的结构成功率提升更大（原生模式 **+23.8 pp**，部分任务从 **0% 直接拉到 100%**），成本相对可控 |
| JSON 基线本来就很强（如 DeepSeek） | XAIOP 的结构提升趋近于 **零**，但 token 消耗反而多花 **2–3 倍**，速度慢 **3 倍以上** |

这不是「XAIOP 全面碾压 JSON」的故事，而是一个更诚实、也更有工程指导意义的结论：**协议的价值是有条件的**，取决于目标模型本身的能力画像。

正式指标定义与已发布快照见：[performance.zh-CN.md](../performance.zh-CN.md)。截图见 [`resources/`](../../resources/)。

## 3. 剩下的瓶颈，已经不在协议设计范围内

测试也暴露了协议解决不了的问题：模型的失败不只是「记不住」，还有「不想守」——高压场景下（超长输出、深层嵌套），模型会主动抄近道，要么退回它训练最深的 JSON / YAML 习惯，要么在协议内部选更省事但更脆弱的写法。

这是**指令遵循纪律性**的问题，不是格式设计能解决的。

---

## 4. 当前定位

XAIOP 目前是**前瞻性实验**，不是 JSON 的替代品，适用场景明确圈定为：

- 成本敏感的轻量模型  
- 指令遵循纪律性强的模型  
- 超长结构化输出场景  

所有指标、代价、失败案例，仓库里都会如实附上——包括提升有限甚至倒退的场景。这不是为了唱好，而是为了让协议在正确的场景下被正确地使用。

| 定位范围内 | 不主张 / 不替代 |
| --- | --- |
| LLM → 应用的结构化抽取，尤其 JSON 括号易坏处 | 用 XAIOP 替代服务间 JSON |
| 按模型能力画像的有条件收益 | 「永远更省 token / 更快」 |
| 如实公开弱收益甚至倒退场景 | 「全面碾压 JSON」 |
