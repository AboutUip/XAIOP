## 1. 目的

XAIOP（eXtensible AI Output Protocol）是一套按行的**游标构造**协议，面向可靠、确定性、流式友好的结构化数据：写者发出进入 / 回退 / 定位 / 重置指令；软件**物化**为 JSON（含中途相位）。

大语言模型是**典型**生成器，不是唯一写者。工具（`encode`）与会话推送（如骨架 WebSocket）使用同一条线。

完整产品立场：**[positioning.zh-CN.md](positioning.zh-CN.md)**。

---

## 2. 问题陈述（信息性）

为确定性程序设计的格式（尤其是 JSON 与 XML）要求一次性吐出全局正确的完整结构。这对长文本、增量与不可靠写者不利：

| 挑战 | 影响 |
| --- | --- |
| 结构一致性要求高 | 长输出更脆弱 |
| 深层嵌套状态难维护 | 失败风险上升 |
| 远距离语法依赖强 | 流式恢复困难 |
| 对部分输出容忍度低 | 增量体验差 |
| 流式生成稳定性不足 | 链路不可靠 |

**理由（信息性）：** XAIOP 围绕**局部游标步骤**与程序侧物化设计，而不是强迫写者模仿括号配对式序列化。

**楔子（信息性）：** 对 LLM，把「记忆问题」变成「逻辑问题」。证据与有条件收益见 **[positioning.zh-CN.md](positioning.zh-CN.md)** · [performance.zh-CN.md](../performance.zh-CN.md)。

---

## 3. 架构位置

```text
写者（LLM · 工具 · 会话推送）
 │
 ▼
XAIOP 协议（游标 IR）
 │
 ▼
解析器 / SDK（物化 · 相位）
 │
 ▼
应用 / 下游系统
```

XAIOP 位于写者与应用消费之间。它不被定义为替代 JSON 总线的通用程序间交换格式。

---

## 4. 目标（规范性意图）

协议设计**必须**追求下列目标：

| 目标 ID | 目标 | 说明 |
| --- | --- | --- |
| G1 | 生成器友好 | 适配增量 / 局部游标书写；避免远距离括号承诺 |
| G2 | 确定性解析 | 不猜测；不以静默修复作为解析语义 |
| G3 | 流式优先 | 支持增量生成与消费；相位友好的物化 |
| G4 | 人类可读 | 可作为文本检查与调试 |
| G5 | 跨写者 | 不依赖特定写者的二进制编码即可跨写者族使用 |
| G6 | 长上下文友好 | 在扩展输出下保持稳定 |

---

## 5. 非目标（规范性）

以下内容明确**不在** XAIOP 作为协议的范围之内：

| 非目标 ID | 陈述 |
| --- | --- |
| NG1 | XAIOP **禁止**被定位为确定性程序之间主要数据交换格式（如 JSON 等）的替代品。 |
| NG2 | 协议**禁止**要求生成器将哈希、校验和、CRC、长度计算或密码学运算作为符合规范的生成义务的一部分。 |
| NG3 | 符合规范的解析器在输入按协议并非良构时，**禁止**被要求修复、推断或猜测生成器意图。 |
| NG4 | 正文编码见 `PROT-CONTENT` / `PROT-SYNTAX`。结构规则见 `PROT-BOUND` / `PROT-HIER` / `PROT-SYNTAX`。 |
| NG5 | 本规范树**禁止**将 SDK API 定义为协议要求。 |

**关于 NG1 的信息性说明：** 产品栈**可以**由程序推送相位（encode、WS 会话）给物化消费端。那是线上的渐进构造——不主张用 XAIOP 替代服务间 JSON 总线。

## 7. 角色

| 角色 | 作用 |
| --- | --- |
| Generator（生成器） | 产生 XAIOP 文本（通常为受提示或约束的 LLM；亦含 encode 工具与会话推送） |
| Parser（解析器） | 按协议确定性解释 XAIOP 文本 |
| Consumer（消费者） | 使用已解析单元或流的应用逻辑 |
| Downstream system（下游） | 存储、变换或展示已消费数据 |

生成器与解析器的精确义务见 `REQ-FUNC` 与 `REQ-STREAM`。
